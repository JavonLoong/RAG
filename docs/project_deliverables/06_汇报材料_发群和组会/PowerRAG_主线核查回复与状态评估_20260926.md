## 2. 四个断点的结论

| # | 断点 | 结论 | 依据 |
|---|---|---|---|
| 1 | 公开书目 JSON 入库 ↔ 主动网络检索获取 | **未接通** | `POST /api/public-books-json/ingest` 只读本地 `input_dir` 里**已经下载好**的 LabelStudio JSON（`api_server/.../public_books_json.py`）；全仓没有搜索、抓取、下载模块 |
| 2 | 带证据关系提交 ↔ 高质量自动关系抽取 | **部分接通** | `/graphs/extract` 确实调 `extract_governed_statements`；`rules` 后端离线可跑（已测）；`small-model` / `llm` 需注册 provider 且由外部注入 `app.state.delivery_graph_extractor`，`create_app` 未预置 |
| 3 | 运行图导入 ↔ 专业图谱对齐、融合、审核发布 | **未接通** | `/api/graphrag/import` 只写运行 `GraphStore`（默认 `reset`），不进治理库、无版本无审核；治理侧没有任何实体对齐 / 设备树 / 术语库 / 既有图谱融合入口 |
| 4 | 发布账本 ↔ 问答/FMEA 实际使用版本 | **可核对，但非自动锁定** | 投影状态记录 `source_version_id`，`/graphs-active/status` 能对账；但 `graphs/{id}/query` 与 `fmea/tasks` 都要求调用方**显式传** `graph_version_id`，是否等于已发布版取决于传参 |

### 断点 1 补充

仓库里与“网络资料”有关的只有三处，都不是自动检索：

- `scripts/ingest_public_books_json_to_chroma.py`、`ingest_all_public_books_snapshots_to_chroma.py`：离线批量入库
- `scripts/download_tsinghua_cloud.ps1`：人工下载清华云的脚本
- `evaluation/reports/skill_vs_model_vs_world_20260923.py`：里面出现 `wikipedia.org`，那是评测题集的“世界知识”参考答案，不是检索能力

所以「检索发现 → 相关性筛选 → 全文获取 → 原始留存 → 候选入库」这一步，目前只有最后一段（入库）有实现。

### 断点 2 补充（量级要说清）

`kg_pipeline/governed_extraction.py` 的 `rules` 后端是**正则**，覆盖面限于已写死的句式：

- 中文：`X的Y由Z导致`、`Y的原因/根因是Z`、`影响/后果是Z`、`通过…发现`、`采用…缓解`
- 英文：`X Y is caused by Z`、`leading to Z`、`detected by Z`、`mitigated by Z`
- 型号：`M701F`、`PG9351FA`、`LM2500`、`STG5-4000F`

它能自动产出**结构合法、带证据、可审核**的候选，但不能当作“高质量关系抽取”。`llm` / `small-model` 通道代码在，运行时缺注入。

### 断点 3 补充

`GraphStore.import_kg_file` / `normalize_kg_payload` 是运行投影工具。`/api/graphrag/import` 默认 `reset=true`，这是给“浏览器里画图后导入看图”用的，按规则**不能**当作正式融合。治理侧没有对齐/合并/权威性/冲突判定入口。

### 断点 4 补充

好处是投影状态是可查的（`project_workspace.projection_states` 记 `source_version_id`、`status`）。风险是问答和出表都靠调用方传版本号：传错版本不会被系统拒绝成“过期”，只会按你传的那版算。这条建议定成规则。

### 03｜原生解析 / OCR / 结构恢复

| 项 | 回填 |
|---|---|
| 当前实现 | native 解析、OCR 任务、失败页重试、调用方回写：**已实现** |

- **Q03.1 真实执行**：`auto` 在 `document_intake.py` 分流；`parser_backend` 枚举 5 个，但**当前环境只装得起 native**，`docling` / `mineru` / `unstructured` 未安装（本机实测），选了会走 `ExternalParserUnavailable`。OCR 引擎现网未预置，默认只能靠 `POWER_RAG_M2_OCR_COMMAND` 或注入。降级是否明确报告：会抛可用性异常，报错是明确的，但**没有“自动降级并记录”的策略**。

- **Q03.3 失败与代价**：页数/块数对账有 `ocr_coverage.json`、`ocr_blocked_pages_evidence.json`；局部失败可定位并 `retry-pages`。**人工修正时间、按页型分类的结构错误率未测量**。

### 07｜高质量关系抽取、知识图谱构建与多源融合

| 项 | 回填 |
|---|---|
| 当前实现 | 候选关系提交（带证据校验）、`rules` 自动抽取：**已实现**；`llm`/`small-model` 通道路径在但**未预置**；对齐与融合：**未实现** |
| 正式集成 | `rules` 已进正式链（已测）；融合未进 |
| 效果与验收 | AC-M4-01 在 120 条关系样本上达标；真实资料全量与漏抽未测 |

- **Q07.1 自动抽取**：不由人工/宿主预先写 `statements` 时，`rules` 能自动产出候选（6 条最小链已验证）。`llm` / `small-model` 需要注册 provider 并且 `app.state.delivery_graph_extractor` 被注入——**`create_app` 里没有这一句**，所以现网默认跑不起来。人工 / 宿主 / 服务端三种产物目前**没有强制归因标签**。
- **Q07.2 语义与覆盖**：`rules` 能抽设备-部件层级、故障-原因-影响-检测-措施五类链；**跨句、跨表格关系不保证**；`model_scope` 与 `knowledge_type` 字段能保留型号差异与知识类型（如 `MODEL_DIFFERENCE`）。是否检查“原文对关系的实际支持”：校验的是类型 + 证据号存在，**不是语义蕴含**。
- **Q07.3 独立质量**：有 `entity_precision/recall`、`relation_precision/recall` 的既有结论（AC-M4-01，样本 120）。缺**独立标注方法说明与分母定义**，也没有对漏抽关系的检查。`confidence` 是抽取方自报，**不能当实测准确率**。
- **Q07.4 既有知识资产**：**仓库里没有可用的既有图谱、设备树、术语库或专家规则文件。**“设备树 / 术语库”字样只出现在构建脚本与测试文本里（`tools/build_powerrag_key_stage_flows.py` 等），不是资产。专家知识的承载形式目前只有评测用的 `fmea_expert.jsonl`、`graph_gold.json`。**当前没有任何入口能把它们接进正式图谱。**
- **Q07.5 实体与层级融合**：**未实现**。没有同名异物 / 同物异名 / 中英别名对齐，也没有“把自动关系挂到既有设备-系统-部件树”的机制。来件举的“润滑油滤器与燃油滤器的堵塞被合成同一工程事实”——目前**没有防线**（只有 `model_scope` 能区分型号）。
- **Q07.6 来源与冲突**：`knowledge_type` 能区分 STRUCTURAL / FAILURE / CAUSAL / EFFECT / DETECTION / MITIGATION / MODEL_APPLICABILITY / MODEL_DIFFERENCE；这是**类型区分**，不是权威性 / 适用范围 / 冲突判定。手册未表述的专家知识**没有独立来源机制**。
- **Q07.7 融合操作**：**不存在**保留/去重/合并/拆分/拒绝/待审/替代这套动作。运行图导入的 `reset` 默认值按规则**不得用于正式融合**。
- **Q07.8 融合验证与效用**：给不出“既有图谱 + 新抽取 → 融合候选 → 审核发布 → 问答/FMEA 使用”的完整示例，因为融合环节不存在。

- **Q09.2 回退边界**：回退原因在 `fallback` 里可追踪；是否限定同一项目/正式资料/版本：**需要按调用参数确认，未做越界测试**。未检索到 / 确无来源 / 冲突 / 模型不可用是否可区分：部分可（`no_answer` 与 `fallback`），冲突不可区分。
- **Q09.3 效果检验**：有同题对比（`compare-rag`）和我们自建的题集报告（`evaluation/reports/cs_long_*`、`three_arm_judged_*`）。这些**不是独立专家金标**；知识融合带来的改善无法评估，因为融合不存在。

## 5. 需要项目/领域方裁决的规则

这些不是实现问题，是口径问题，需老师或项目负责人拍板后再改代码：

1. **来源类型与范围**：网页、既有图谱、专家知识分别以什么来源类型、什么版本、什么审核状态进入正式结论？适用范围如何标注？
2. **证据口径**：网页没有页码时用什么做稳定定位（版本快照 / 段落区块 / 渲染页）？既有图谱用什么可验证来源对象？——不能虚构页码。
3. **自动抽取归因**：服务端自动、Skill 宿主代填、人工编写三种产物如何在图上留痕区分？
4. **FMEA 正式入口**：`/api/delivery/fmea` 与 `/api/v1/fmea` 哪条是正式交付线，另一条如何定位？
5. **验收阈值与责任**：抽图/融合/问答/FMEA 的指标、金标规模、阈值与签字人。
6. **运行方式**：目标机是本地模型、已登记 provider，还是 Skill 宿主辅助？决定“哪些环节必须软件自己完成”。

## 6. 下一步最小验证清单（不预设工期）

按“先证实可复用资产、再定缺口”的原则，建议按顺序只做这几件：

1. 在目标 Windows 机上，用**一套真实资料**跑通：上传 → 解析 → 审 → 发布 → `graphs/extract`（rules）→ 审图 → 发布 → `resync` → FMEA → 导出 → 验收包。产出一份端到端记录。
2. 同一批资料，让**领域专家**给出参考关系，量出 rules 抽取的漏抽与误抽（这就是 Q07.3 缺的独立分母）。
3. 补 AC-E2E-01 / AC-E2E-02：**两名角色**经正式界面完成主闭环与恢复闭环并签字。
4. 做一次**网络来源试点**：人工给定 3–5 个公开来源，先做“来源登记 + 原始留存 + 入候选”，把来源字段（URL、发布者、获取时间、哈希、适用范围）落进数据模型，再谈自动检索。
5. 就上面第 5 节的六条规则，请老师/项目方给一次明确答复。

完成 1–5 之后，才能判断“哪些是已证实可复用资产、哪些是能力缺口、哪些是未决规则”，再编制详细开发计划。
