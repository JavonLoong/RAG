## 2. 阶段一实测：资料治理与正式发布

### 2.1 跑通的部分

| 步骤 | 结果 |
|---|---|
| `POST /api/delivery/projects` | 201 |
| `POST /api/delivery/documents/intake`（native，44 篇） | **44/44 = 200**，状态 `parsed` |
| `review`（approve） | **44/44 = 200** |
| `publish` | **44/44 = 200** |
| 治理库落库 | `document_versions` 44（全部 published）、`source_assets` 44、`evidence_locators` **3848**、`reviews` 46 |
| 每篇证据数 | 最少 11，最多 273，平均 87.5 |
| `documents-index/rebuild` | 200，`indexed_chunks` **3848**，集合 `governed_materials` |
| `GET /api/delivery/documents-search?q=有机朗肯循环&mode=hybrid` | 200，返回带 `evidence_id` 的真实命中 |
| 单篇解析耗时 | 0.25–4.12 秒（14 MB 那篇 3.78 秒） |

**结论**：上传 → 解析 → 审核 → 发布 → 检索投影 → 检索，这条主干在 44 篇真实 PDF 上跑通，且是全自动串起来的。这是可以对外演示的部分。

### 2.2 不通：证据没有页码（阶段一最严重）

**实测**：`evidence_locators` 共 3848 条，`page` 非空的 **0 条**；`block_id` 非空 3848 条。

```
evidence_locators          3848
evidence_with_page            0   ← 
evidence_with_block        3848
distinct_pages                0
```

**但 M2 明明抽到了页码**。同一篇的入库切片元数据里：

```
page_nums      : "[1]"
citation_anchor: "xxx.pdf#pages=[1]#chunk=0"
boundary_id    : "xxx.pdf::page-1"
```

**根因（精确定位）**：`storage_layer/governance_store.py` 的 `_chunk_to_payload` 只认这几个键：

```python
page = get("page") or get("page_num") or metadata.get("page") or metadata.get("page_num")
```

而切片层 `chroma_rag_poc/chunking.py` 写的是 **复数** `metadata["page_nums"]`（值是 `"[1]"` 这种字符串）。键名对不上 → 页码恒为 `None`。

**影响**：阶段一对外的核心承诺是「证据能回到手册页码」。现在治理库里所有证据的页码都是空的，`GET /api/delivery/evidence/{id}/open` 也回不到页。这是**一个键名的接缝问题**，但会让整条证据链的门面失效。

> 这一条正是老师问的「代码有了某项能力后，是否在整体流程里能 work」的典型：M2 有页码能力、M3 有页码字段、两边就是没接上。

### 2.3 不通：可选解析后端静默失效

请求 6 个后端各跑一遍同一篇 PDF：

| 请求 `parser_backend` | HTTP | `processing_plan.runtime` | 提示 |
|---|---|---|---|
| `native` | 200 | native / used | — |
| `auto` | 200 | native / used | — |
| `deepdoc` | 200 | native / used | **无提示** |
| `mineru` | 200 | native / used | **无提示** |
| `unstructured` | 200 | native / used | **无提示** |
| `docling` | 200 | docling / fallback_to_native | 有 warning |

四个后端的产物 `content_hash` 完全相同，说明实际都是 native。《0923》文档里列的 `deepdoc / mineru / unstructured` 三个后端名，**在接口上存在、在行为上不存在**；其中 `mineru`、`unstructured` 连"我降级了"都不说。只有 `docling` 老实标注了 `fallback_to_native`。

（`docling` / `mineru` / `unstructured` 三个包本机未安装，实测确认。）

### 2.4 降级：向量是 hashing 占位

```
embedding_backend : hashing
embedding_model   : hashing-1024
embedding_warning : Local sentence-transformer model not found for 'Qwen/Qwen3-Embedding-0.6B',
                    falling back to hashing.
```

`models/`、`local_models/` 都是空的，也没有设 `RAG_EMBEDDING_MODEL_PATH`，所以自动降级成哈希向量。检索**能跑**，但语义召回质量不能当正式指标。

另外：`chromadb 0.5.3` 装的是旧版，和 `numpy 2.x` 不兼容（`np.float_` 已移除），**裸 `import chromadb` 会直接报错**。它现在能用，是因为 `chroma_rag_poc/__init__.py` 里有个 `_patch_numpy_aliases_for_legacy_chromadb()` 在打补丁。任何绕过这个包的独立脚本都会挂，打包部署时也不能丢这个补丁。

### 2.5 未验证：OCR

这批 44 篇都有文本层，`use_ocr=auto` 时状态直接是 `parsed`、不产生 OCR 任务，所以 OCR 链路这次**没有被验证**。代码里 OCR 默认没有 provider，要靠 `POWER_RAG_M2_OCR_COMMAND` 或注入 `app.state.m2_ocr_provider`。

### 2.6 不通：只有题录的 63 条文献进不来

唯一和外部题录沾边的入口是 `POST /api/public-books-json/ingest`。拿这批材料试：

```
500  {"detail":"JSON : top-level JSON must be a list? ..."}
```

它要求的是 **LabelStudio 导出的 JSON 数组**，而且要的是有正文的标注结果，不是题录 CSV。结果：

- 只有题录（无全文）的 63 条文献，**没有任何接口能接收**；
- 就算把 CSV 硬塞进去，也进的是 Chroma 快路径集合，不是治理链。

来源字段（URL、发布者、获取时间、许可范围）在 `document_versions` / `source_assets` 里也没有结构化列，只能塞 `metadata`。

## 3. 阶段二实测：图谱构建与融合治理

### 3.1 跑通的部分

对 44 篇已发布资料跑 `POST /api/delivery/graphs/extract`（`backend=rules`）：

| 步骤 | 结果 |
|---|---|
| extract | 200，6.11 秒，45 个候选 → **30 条关系** |
| 证据绑定 | 30/30 都有 `evidence_ids` |
| `review`(approve) → `publish` | 200 → 200 |
| `resync` | 200，同步出 **55 节点 / 30 边 / 30 证据** |
| `graphs-active/status` | `projection.status = ready`，`source_version_id = graph:v1` |

**结论**：候选关系 → 证据校验 → 审核 → 发布 → 同步运行图 → 投影可查，这条链是通的，而且**能自动跑**。

### 3.2 人工提交关系：跑通且有门禁

`POST /api/delivery/graphs/candidates` 提交一条人工写的关系（故意给假证据号）：

```
200，进入 graph:v1，status = needs_review
quality_issues: [{
  "code": "missing_source_evidence",
  "message": "statement #1 has no evidence or references evidence outside the selected material versions.",
  "severity": "error"
}]
```

人工关系能进治理链，**且缺证据会被拦下**。这个门禁是对的。

### 3.3 不通：真实文献上抽取质量不可用

30 条关系只有两个类型：

```
CAUSED_BY        28
HAS_FAILURE_MODE  2
```

最小故障链需要 6 类（`HAS_FAILURE_MODE` / `CAUSED_BY` / `HAS_EFFECT` / `DETECTED_BY` / `MITIGATED_BY` / `PART_OF`），**真实文献上只出了 2 类**，`HAS_EFFECT`、`DETECTED_BY`、`MITIGATED_BY`、`PART_OF` 全为 0。

原因是 `kg_pipeline/governed_extraction.py` 的 rules 后端是**写死的正则**，针对的是「燃气轮机润滑油系统的过滤器堵塞可能由油液污染导致」这类中文故障句。放到英文热力学论文上，它只匹配到少量残片。

**并且产生了错误实体**。生成出来的 FMEA 第一行：

```json
{
  "component": "The",
  "failure_mode": "scatter in the results",
  "cause": "insufficient precision in the reported data from t",
  "equipment": null,
  "effect": null,
  "detection_method": null,
  "recommended_action": null
}
```

`component = "The"` —— 正则把英文冠词吃成了部件名。而这行数据**正常通过了逐字段审核并发布了**。

**这一条很关键**：门禁只校验「类型合法 + 证据号存在」，**不校验语义是否成立**。所以垃圾数据能一路走到正式发布。

### 3.4 不通：图问答没走图

```
POST /api/delivery/graphs/graph:v1/query
  question      : 有机朗肯循环的工质选择依据是什么
  requested_mode: graphrag
  mode_used     : ordinary_rag     ← 回退
```

图上没有对应路径，直接回退普通检索。回答内容来自 `documents-search` 的原文片段（而且原文里有 OCR/编码噪声，如 `�?` 乱码）。

也就是说：**阶段二做出来的图，在这次真实语料上没有被问答用到**。

### 3.5 FMEA 链路通、内容不通

| 步骤 | 结果 |
|---|---|
| `POST /fmea/tasks` | 200，`item_count = 2` |
| `review`(approve) → `publish` | 200 → 200 |
| `export json / csv / docx` | 200，74902 / 65545 / 37827 字节 |

44 篇文献 + 30 条关系，只生成 **2 行**，且字段如上所述是错的。导出文件的字节数是真实的、行数是一致的，但**内容不可用**。

`llm` / `small-model` 抽取通道代码在，但 `create_app` 没有设 `app.state.delivery_graph_extractor`，所以现网默认只有 rules。

### 3.6 不通：多源融合完全没有

老师主线图里「已有图谱 / 设备树 / 术语库 / 专家知识 → 对齐 | 融合 | 冲突检测 | 人工修订」这一整块，实测：

- 治理侧**没有任何对齐/融合/冲突入口**（89 个 `/api/delivery` 接口里没有）；
- 仓库里**没有设备树、术语库、既有图谱数据文件**；
- 只有 `model_scope` + `knowledge_type` 两个字段能区分型号和知识类型，这不是融合。

### 3.7 不通：问答对生成

全仓无实现，`evaluation/` 里的题集都是人工编写的。

## 4. 专题一：文本的人工标注识别

老师的原话是「比如文本的人工标注识别」。实测结论：**这条能力在整体流程里不存在**。

**(1) 全站没有标注端点。** 扫 218 条接口，路径里含 `annot` 或 `label` 的：**0 条**。

**(2) 名字叫 annotation 的模块干的不是标注。** `data_pipeline/m2_annotation.py` 的注释是「Language, lossless repair, structural IDs, and aligned translation」——做的是语言识别（zh/en/mixed）、OCR 断行修复（`latin_hyphenation`、`cjk_soft_linebreak`）、以及对照翻译。**不含人工标注**。

**(3) LabelStudio 是外挂的，没闭环。** 相关的只有：

- `POST /api/public-books-json/ingest`：读 LabelStudio 导出的 JSON → 写 Chroma 集合 `public_books_labelstudio`（**快路径**，不是治理链）。本次实测 500。
- `scripts/audit_public_books_labelstudio_json.py`、`evaluation/reports/_inventory_labelstudio_json.py`：**审计/清点**脚本，不是导入。

也就是说：标注结果能进来的只有"事后批量入库到另一个集合"，**没有标注任务下发、没有回填、没有版本、不进治理链**。

**(4) 治理链真正能接收的人工输入只有两处**（这是好消息，也不是标注）：

- `POST /documents/{version_id}/review` 的 `decision` + `corrections`：人可以改正文/字段，改正文会 `revise` 出新版本。
- `POST /graphs/candidates` 的人工 `statements`：人可以写关系，必须带证据，否则被拦。

**(5) 附带发现**：切片元数据里已经有 `labels: {'Para': 1}` 这种标注标签，说明 LabelStudio 的标注**能带到切片里**，但没有任何地方消费它，治理库也没有块级标签字段。

## 5. 专题二：知识图谱的交互编辑

这一条我实测出了一个**会破坏正式数据的反例**。

**能做图交互的是 M2 知识组织页的运行图**：`/api/graphrag/import`（写图）、`/export`、`/reset`、`/community/detect`。浏览器里画完图能导进去、能看图。

**但它和治理图不是一套东西，却写同一个文件。** 代码定位：

```python
# routes_delivery.py  ——治理图同步用的路径
graph_path = persist_dir / "graph_store.sqlite"

# routes_graphrag.py  ——M2 图导入的默认路径
db_path = (Path(request.app.state.persist_dir) / "graph_store.sqlite").resolve()

# 而且导入默认 reset=True
class GraphImportRequest(BaseModel):
    reset: bool = True
```

**实测后果**（`thermo_graph_clobber_20260927.json`）：

| 时点 | 运行图 | 投影状态 |
|---|---|---|
| 发布 + `resync` 之后 | 55 节点 / **30 边** / 30 证据 | `ready`，`item_count 30` |
| M2 页面做一次默认图导入（2 个节点） | 2 节点 / **1 边** / 0 证据 / 实体类型 Unknown | **仍然 `ready`，`item_count 30`** |
| 治理库里的 `graph:v1` | 30 条关系（**没坏**） | — |

三个问题一起出现：

1. **治理图投影被清掉了**——30 条带证据的边变成 1 条没证据的边，`evidence_count` 归零。
2. **没有任何报警**——`/graphs-active/status` 照旧报 `projection.status = ready`、`item_count = 30`、`source_version_id = graph:v1`。投影记录是**过期账本**，不和真实库对账。
3. **导入的边进不了治理链**——没有证据、实体类型 `Unknown`、不产生版本、不需要审核。

**这条直接回答了老师的问题**：交互编辑这个能力，代码里有、界面上能点，但**放进整体流程里 not work，反而会把阶段二的正式产物打坏**。

## 6. 需要开发的清单（按先后）

**P0 先修接缝，不改能力**

| # | 问题 | 改哪里 |
|---|---|---|
| 1 | 证据页码全空 | `governance_store._chunk_to_payload` 认 `page_nums`（复数、`"[1]"` 形式）；或 `chunking.py` 同时写 `page_num`。验收看 `page` 非空率 |
| 2 | 交互编辑打坏治理图投影 | 运行图与治理图**分成两个文件**（`runtime_graph.sqlite` vs `graph_store.sqlite`）；或导入默认 `reset=False` 且禁止写治理投影路径 |
| 3 | 投影状态会说谎 | `graphs-active/status` 增加与真实库的对账（比对 `edge_count`），不一致就报 `stale` |
| 4 | 4 个解析后端静默走 native | `_load_records_for_profile` 对 `deepdoc/mineru/unstructured` 显式报 `unsupported_backend`，或在文档里删掉这三个名字 |
| 5 | chromadb 靠 monkey-patch 才能用 | 固定兼容版本组合，或把补丁移到包初始化之外；独立脚本要能单独跑 |

**P1 让能力在流程里真正生效**

| # | 目标 | 说明 |
|---|---|---|
| 6 | 正式嵌入 | 目标机放 `Qwen3-Embedding-0.6B`，或明确允许联网；否则检索只是占位 |
| 7 | 抽图质量 | 把 `llm` / `small-model` 接进 `app.state.delivery_graph_extractor`；给 rules 加领域词典+停用词，先消灭 `component="The"` 这类错误 |
| 8 | 语义门禁 | 现在只校验「类型合法 + 证据号存在」，需要加一层「原文是否支持该关系」的检查，否则垃圾能发布 |
| 9 | 63 条题录入库 | 新增题录入库接口，让无全文的文献以「只有题录」的明确状态进治理链，不假装有全文 |

**P2 补阶段二缺的能力**

| # | 目标 |
