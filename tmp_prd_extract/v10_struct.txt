P008|
P009|产品决策  优先建设“证据治理与 FMEA 交付工作台”，而不是再扩展一个泛化问答页面。当前系统的核心后端闭环已经可执行，最大的产品断层是审核人无法通过主控制台完成治理操作。
P010|0. 执行摘要
P011|PowerRAG 已具备本地文档接入、OCR/解析、正式资料版本、受 Schema 约束的图谱、GraphRAG 问答、FMEA 生成、人工审核、发布、导出和问题回流等后端能力。仓库专项验证在本次审阅中通过 32 项测试，但当前主控制台没有接入 /api/delivery，关键能力主要停留在 API、脚本和测试层。
P012|本 PRD 定义一个面向知识工程师与燃气轮机领域审核专家的本地工作台：用统一任务队列贯穿 M2–M5，在同一界面完成原页与解析结果对照、版本审核与发布、图谱语句证据审计、FMEA 逐字段校核、双格式导出验证以及问题回流。
P013|MVP 的成功标准不是“页面可展示”，而是让一名审核人无需调用 API 或改 JSON，即可从一份待审核资料走到一个带完整证据链、经人工批准且可一致导出的 FMEA 成果。
P014|1. 背景与机会
P015|1.1 当前系统定位
P016|PowerRAG 是一个 local-first 的 RAG / GraphRAG 工作台，当前可运行产品由 FastAPI 后端、单文件前端控制台和 Electron 桌面壳组成。其差异化价值不是单纯聊天，而是把设备资料、图谱关系、检索证据和工程交付成果连接起来。
P017|
P018|判断依据：README.md、docs/GOVERNED_DELIVERY_WORKFLOW.md、routes_delivery.py、core_domain/delivery.py、governance_store.py，以及本次 32 项专项测试结果。
P019|1.2 核心问题
P020|能力不可操作：后端有完整治理接口，但主控制台未检出 /api/delivery 调用；非开发人员无法完成正式审核。
P021|上下文被割裂：资料、图谱与 FMEA 各自有版本和证据，但缺少一条可视化血缘链来解释“这个字段从哪里来”。
P022|发布风险不可见：阻断级质量问题由后端守门，但用户在点击发布前无法快速理解哪些问题必须先处理。
P023|任务无法管理：现有接口以单个 ID 查询为主，资料与 FMEA 缺少分页列表和跨阶段审核队列。
P024|交付价值未显性化：系统已经能产出可审查 FMEA，但主产品仍被理解为“RAG/GraphRAG 演示工具”。
P025|1.3 产品机会
P026|将已有治理后端包装为真实的人机协作工作流，可以把 PowerRAG 从“技术能力集合”推进为“工程知识交付系统”。这项工作复用现有 M2–M5 能力，新增价值集中在任务组织、审核体验、发布门禁、血缘可视化与必要的列表型 API，投入相对可控，且能形成清晰的演示与验收闭环。
P027|2. 产品定义
P028|2.1 一句话定位
P029|定位  面向电力装备知识工程师与领域专家的本地证据治理工作台，把文档解析、正式资料、受控图谱和 FMEA 成果变成可审核、可追溯、可回滚的交付链。
P030|2.2 目标用户

P032|2.3 产品原则
P033|证据优先：任何衍生事实都能回到稳定的文档版本、文件、页、块或表格定位。
P034|人工决定可追踪：批准、驳回、修改、发布与回滚必须记录操作者、时间和理由。
P035|先门禁，后发布：阻断问题不能靠普通确认绕过；按钮状态必须解释原因。
P036|未知保持未知：缺失字段显示为空与原因，不用模型常识补齐；不自动生成无依据的 S/O/D 或 RPN。
P037|本地优先：MVP 延续 Electron + FastAPI + SQLite/本地存储，不引入云端多租户依赖。
P038|渐进披露：总览显示待办和风险，细节通过证据抽屉、版本差异和审计时间线展开。
P039|3. 目标、非目标与指标
P040|3.1 MVP 目标
P041|打通从待审核资料到已发布 FMEA 的单人完整操作链，不要求用户调用 API。
P042|让审核人对每个资料问题、图谱语句和 FMEA 字段看到对应证据、版本与状态。
P043|把发布门禁和失败原因前置展示，避免“点击后才知道不能发布”。
P044|提供统一任务队列、跨阶段血缘与反馈回流，使问题能回到正确根因模块。
P045|保持现有治理不变量，不因前端便捷性削弱证据、审核或版本约束。
P046|3.2 非目标
P047|不在 MVP 中建设托管式多租户 SaaS、组织级权限和实时多人协作。
P048|不替换现有解析、OCR、向量库、图存储或 GraphRAG 算法内核。
P049|不以本 PRD 承诺提升实体关系抽取精度；模型效果单独走评测体系。
P050|不自动生成无政策依据的严重度、发生度、探测度或 RPN 评分。
P051|不在首版重构整个单文件前端；先以独立路由/模块接入，稳定后再拆分工程。
P052|不把移动端作为首版验收范围。

P057|4. 核心用户旅程
P058|主流程以“一个交付批次”为工作单元，批次将文档版本、图谱版本、FMEA 任务和审核记录串联起来。用户始终在当前批次内操作，避免复制 ID。
P059|
P060|4.1 关键状态机
P061|资料与图谱状态：candidate → needs_review → published → retired。回滚不会覆盖旧版本，而是生成或恢复可审计版本关系。
P062|FMEA 状态：queued → running → needs_review → approved → published；异常进入 failed。所有迁移保留 from_status、to_status、actor、reason 与 created_at。
P063|门禁规则  资料只在存在证据且最新人工审核为 approve 时发布；图谱只从已发布资料构建且每条语句必须绑定范围内证据；FMEA 只从已发布图谱生成并在人工批准后发布。

P078|5.4 图谱审核页
P079|默认表格视图：以语句为最小审核单元，列出主语/类型、关系、宾语/类型、知识类型、型号范围、置信度和证据状态。
P080|问题优先筛选：未知类型、未知关系、端点不合法、证据缺失/越界、来源冲突、低置信度。
P081|证据抽屉：点击语句后显示所有 evidence_id 的原文、文件、页、块以及资料版本。
P082|关系图视图：用于理解局部路径，不作为唯一审核界面；大图自动降级为表格/搜索。
P083|发布前检查：证据审计、阻断问题、来源资料状态与 GraphStore 同步目标必须全部可见。
P084|5.5 FMEA 交付页
P085|任务头：显示所选资料版本、图版本、模板版本、状态、创建人和时间。
P086|交付表：equipment、component、failure_mode、cause、effect、detection_method、recommended_action 七个最小专业字段。
P087|字段证据：每个非空字段显示证据数量徽标；点击打开证据抽屉；无证据字段显式标红。
P088|未知与冲突：空值保持为空并显示原因；冲突信息不可被隐藏，需人工确认或回流。
P089|交付动作：修改、批准、驳回、发布、下载 JSON/CSV、运行一致性验证。

P094|7. 数据与业务规则
P095|7.1 证据显示规则
P096|每条证据最少显示 document_version_id、chunk_id、source_file、text；有值时显示 page、block_id、table_id、image_id。
P097|界面中任何证据徽标都必须可点击并解析到证据详情；无法解析的 evidence_id 视为阻断错误。
P098|图谱证据只能来自该图版本选择的已发布资料版本；越界证据不能通过普通审核绕过。
P099|FMEA 的证据按字段绑定，不只在整行或任务级展示；非空字段无证据时不得发布。
P100|原文、人工修订内容与模型生成内容在视觉上必须区分，避免把候选误认成源证据。

P126|14. 待产品确认的问题
P127|MVP 的第一试点对象是否固定为燃气轮机/FMEA，还是需要同时覆盖通用企业知识库？建议先固定燃气轮机，以现有 Schema 与模板闭环。

P130|图谱语句的人工修订是直接保存 corrections，还是创建新的图候选版本？建议任何内容变更都生成新候选版本。
P131|首版是否需要 FMEA 自定义列与企业模板导入？建议 P0 只支持版本化最小模板，P1 再做模板映射。
P132|是否需要在首次试点纳入 S/O/D 与 RPN？建议否，除非提供已批准、证据可绑定的评分政策。
P133|试点成功由谁签字：知识工程师、领域专家还是交付负责人？建议资料/图由领域专家审批，FMEA 由领域专家与交付负责人共同确认。
P134|15. Definition of Done
P135|AC-01 至 AC-12 在代表性原生 PDF、扫描 PDF、DOCX、图片、中英文、OCR 超时/漏页、图冲突和 FMEA 缺证据场景下通过。
P136|用户仅通过 Electron/Web 控制台完成一条 M2–M5 全链，过程中不需要复制对象 ID 或调用 Swagger。
P137|每个发布成果可解析到稳定证据定位；所有人工决定、状态迁移、发布、回滚与回流均可查询。
P138|资料索引、治理图谱、活动 GraphStore 与 FMEA 请求版本一致；不一致时系统明确阻断。
P139|JSON/CSV 导出一致性为 100%；任何无依据的字段保持 null；阻断问题逃逸数为 0。
P140|新增 API 与前端合同有自动化测试；专项 M2–M5 回归继续通过；演示数据和操作手册可重复运行。
P141|试点完成至少 10 个代表性任务，记录审核周期、回流原因和用户反馈，并据此确认 P1。
