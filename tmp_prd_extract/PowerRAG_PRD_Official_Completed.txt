PowerRAG 可信知识交付系统 PRD
——面向电力装备的本地优先、证据治理型 RAG / GraphRAG 知识交付系统
一、文档目的与产品定位
（一）文档目的
本文件定义 PowerRAG 的产品定位、目标用户、业务边界、端到端产品要求、技术约束和 V1 验收标准，是产品设计、研发实现、领域审核和交付验收的统一依据。文中“必须”表示 V1 发布门槛，“应”表示 V1 优先能力，“可”表示不影响 V1 发布的增强能力。
（二）产品定位
PowerRAG 是面向燃气轮机及其他电力装备的可信知识交付系统。它把 PDF、扫描件、Word、图片、故障记录和专业标准转化为可检索、可追溯、可审核、可版本化的正式资料、证据问答、领域图谱和 FMEA 等工程成果。
PowerRAG 不以“回答得像人”为主要价值，而对从来源到成果的完整证据链负责：任何正式结论都能回到确定的源文件、资料版本、页码和结构块；任何正式发布都有明确审核决定、配置血缘和可回滚版本。
（三）产品类别与形态
产品类别为证据治理型 RAG / GraphRAG 知识交付系统。V1 以 Windows Electron 桌面端和本地 Web 控制台为主要入口，以 FastAPI 本地服务和可调用 API 为能力接口，以项目目录、治理数据库、检索投影和图投影为本地数据载体。
桌面端、Web 页面、API、任务中心和验收工作台都是产品载体，不是产品定位本身。产品价值由“资料可信化—知识可检索—关系可治理—成果可交付—问题可回流”的闭环共同构成。
（四）核心价值
1. 资料可用：复杂版面、扫描件、表格、图片、乱码、缺页和阅读顺序风险不会被静默扁平化。
2. 结论可证：答案、图谱语句和专业字段分别绑定可解析证据，而不是只显示一个无法复核的引用标签。
3. 过程可审：候选、待审核、已发布和已退役状态明确，修改、批准、驳回、发布、回滚和反馈均可追踪。
4. 成果可交付：知识被转化为可审核、可导出、可复现的工程成果，而不是停留在一次性聊天或图谱展示。
5. 部署可控：敏感资料默认留在用户环境，外部模型调用受项目数据策略约束并留下调用审计。
（五）V1 边界与非目标
V1 服务单机或局域网内的单团队、多个隔离项目，首个验收领域锁定燃气轮机资料与 FMEA 交付。V1 不建设托管式多租户 SaaS，不替换 PLM、EAM、CMMS 或质量管理系统，不覆盖所有工业领域，也不承诺在没有真实语料和专家金标准时达到生产准确率。
V1 不把模型生成结果直接定义为正式知识，不把知识图谱等同于可视化图片，不强制引入 Neo4j 或外部消息中间件，不在没有批准评分政策时自动补齐 FMEA 的 S/O/D 或 RPN。
二、目标用户、职责与核心任务
（一）知识工程师
负责创建项目、接入资料、选择解析策略、处理 OCR 和结构问题、维护正式资料版本、构建索引与图谱、追踪任务失败。其核心目标是把原始资料稳定地转化为可被检索和下游消费的正式知识资产。
（二）设备与可靠性领域审核人
负责对照原页审核解析块、实体关系和 FMEA 字段，识别型号差异、来源冲突与证据不足，作出批准、修改或驳回决定。其核心目标是直接判断“原文是否支持该结论”，而不是阅读模型自我解释。
（三）研发、运维与检索用户
围绕设备结构、故障模式、原因、影响、检测和建议措施检索资料与提问，查看普通 RAG 或 GraphRAG 的证据、路径、版本和回退原因。证据不足时接受明确拒答，而不是获得无来源的确定性答案。
（四）项目与交付负责人
负责确认交付范围、使用的资料/图谱/模板版本、责任人和发布结论，查看风险、审计和验收状态，导出成果与项目包。其核心目标是证明本次交付能复现、能回滚、能说明已验证与未验证范围。
（五）测试与验收负责人
负责维护代表性文件、专家问题集、图谱金标准、FMEA 复核结果、性能记录和角色化端到端签字，使用验收工作台形成带文件哈希和责任人的正式验收包。
三、产品对象、状态与治理原则
（一）核心产品对象
系统以 Project、SourceAsset、Document、DocumentVersion、EvidenceLocator、IndexSnapshot、GraphSchema、GraphVersion、FMEATemplate、FMEATask、DeliveryTask、ReviewDecision、AuditEvent 和 AcceptancePackage 为核心对象。对象之间通过 project_id、来源版本、内容哈希和配置哈希形成可查询血缘。
（二）状态模型
资料、图谱和专业成果必须区分 candidate、needs_review、published 和 retired；长时任务必须区分 queued、running、needs_review、completed、failed 和 cancelled。状态迁移由明确动作触发，不以页面展示或文件存在代替正式状态。
（三）不可破坏的治理原则
1. 每个衍生事实必须指向稳定证据定位，至少包含资料版本、源文件和 chunk/block，可用时必须包含页码和版面位置。
2. 资料只有在源证据存在、阻断质量问题已解决且最新人工决定批准后才能发布。
3. 图谱候选只能消费已发布资料版本；未知类型、未知关系、非法端点、证据缺失或证据越界必须阻断。
4. 别名和重复可以归一，但型号差异和来源分歧不得被静默合并；冲突必须保留供人工复核。
5. FMEA 只能基于已发布图谱和一致的资料版本；每个非空专业字段独立绑定证据，未知值保持 null。
6. 所有批准、驳回、修改、发布、回滚、重同步和反馈修复都必须留下持久审计。
7. 上游资料修订后，受影响的索引、图谱和成果必须被标记为过期，并重新生成或重新验证。
四、端到端业务流程
（一）建立项目与数据基线
用户创建项目并确定设备范围、资料清单、数据策略、领域 Schema、模型/解析 Provider、FMEA 模板、验收集和责任角色。系统为项目建立独立目录、治理库和可重建投影，不允许不同项目默认共享数据。
（二）源资料接入、解析与质检
系统先保存不可变源资产和 SHA-256，再按文件类型与文本质量选择原生解析、OCR 或外部版面解析。每一页必须产生文本/结构结果或明确阻断问题；部分页失败不得导致其余成功页丢失，也不得静默发布整份资料。
（三）人工修订与正式资料发布
审核人通过原页与解析块对照完成修改、批准或驳回。内容修改必须创建新资料版本，源资产保持不变。发布后默认检索只消费每个 document_id 的当前正式版本，旧版本保留用于比较、追溯和回滚。
（四）索引、检索与证据问答
已发布资料驱动关键词、语义和混合索引快照。回答流程先检索证据，再判断是否生成；答案显示资料版本、文件、页码、块号和相关度。没有达到证据门槛时返回“证据不足”或回退，不允许使用模型常识补齐。
（五）图谱构建、审核与 GraphRAG
系统按已批准 Schema 从正式资料生成候选实体关系，执行类型、端点、型号、证据和冲突校验。审核通过后发布不可变图版本并同步图投影。GraphRAG 返回图路径、图证据、文本证据、图版本、路由和回退原因；图质量不足时使用普通 RAG。
（六）FMEA 生成、审核与交付
用户选择已发布图版本、与其一致的资料版本和已批准模板创建 FMEA 候选。设备、部件/系统、故障模式、原因、影响、检测方法和建议措施分别绑定证据。领域审核通过后才能发布并导出 JSON、CSV 和正式 DOCX。
（七）反馈修复与下游重验证
答案、图谱语句和 FMEA 字段都可发起问题。系统按根因路由到源资料、解析、正式资料、图谱或成果模块，生成实际修复运行；上游对象改变后重建投影并重新审核受影响下游，不允许只登记反馈而不执行修复。
（八）验收与发布
验收负责人从工作台领取开放项、填写结构化金标准、上传原始证据并记录审核人和时间。系统实时计算门禁，生成 acceptance.json、acceptance.md、work_items.json 和递归 SHA-256 manifest。没有真实证据的门禁保持未评测或失败，不用样例数据改写结论。
五、产品功能需求
（一）P0 项目与任务管理
PR-P0-01 项目隔离。所有源资产、资料版本、索引快照、图谱版本、FMEA 任务、审核、日志和导出必须带 project_id；不同项目默认不可互查。
PR-P0-02 任务中心。提供资料处理、OCR 页重试、索引、图谱抽取、社区摘要、GraphRAG 批量评测、FMEA 和反馈修复任务；支持状态、阶段、时间、类型、责任人和严重度筛选。
PR-P0-03 任务状态。长时任务统一返回状态、进度、当前阶段、错误码、关联对象、重试次数、租约/心跳和是否可重试；支持取消、重试、指派和评论。
（二）P0 资料接入与解析
PR-P0-04 文件接入。支持原生 PDF、扫描 PDF、DOCX、图片和 TXT；Web 主路径使用 multipart，Electron 可使用受限本地路径交接，20 MB 以上文件不得走 Base64 JSON 主路径。
PR-P0-05 源资产。保存不可变原文件、文件名、大小、MIME、SHA-256、页数、接入时间、创建人和项目；重复文件预检提示，不自动覆盖且不产生幽灵记录。
PR-P0-06 解析路由。根据文件类型、可提取文本比例和项目策略选择 native、OCR 或外部 parser；依赖未安装、服务不可达或能力不匹配时显示明确状态。
PR-P0-07 结构证据。解析输出必须保留 heading、paragraph、table、image、caption、bbox、reading_order、页码和块号；表格错位或阅读顺序风险进入阻断审核。
PR-P0-08 页级恢复。单页失败、空结果或超时不丢弃其他页；可只重跑所选页并生成新版本，记录引擎、耗时、置信度、尝试次数和错误。
PR-P0-09 原页对照。审核人可按页查看登记源文件的原页和解析块，定位表格/图片/文本并修改；修改产生新版本，不覆盖源证据。
（三）P0 正式资料与检索
PR-P0-10 资料台账。按项目、状态、文件名、document_id、版本、问题代码和时间稳定分页；可进入审核包、版本比较、回滚和证据打开。
PR-P0-11 发布门禁。存在源证据、阻断问题已解决且最新人工决定为 approve 才能发布；发布请求携带认证 actor、comment、幂等键和 expected version，冲突返回 409。
PR-P0-12 索引快照。记录资料版本集合、嵌入 Provider、模型、维度、分块配置、配置哈希、构建人和构建时间；测试用 hashing 嵌入不得伪装为正式模型。
PR-P0-13 检索模式。提供关键词、语义和混合检索；检索范围按项目和正式资料版本限定，并显示采用模式、得分和证据。
PR-P0-14 引用打开。检索和回答引用可解析到登记源文件的页、块、表或图；路径越界或定位失败视为 citation_integrity_error，不展示伪引用。
（四）P0 图谱与 GraphRAG
PR-P0-15 Schema 版本。实体类型、关系类型、端点规则、知识类型、别名、型号归一、最低置信度和证据政策按项目版本化；图版本记录完整 Schema ID、版本和哈希。
PR-P0-16 抽取 Provider。rules 为可审计基线；small-model/LLM 模式必须使用已注册 Provider，记录模型、提示词版本/哈希、温度、超时、重试、耗时和响应摘要哈希，未配置时不得显示为成功。
PR-P0-17 图谱审核。按关系、实体类型、型号、置信度、证据状态和问题代码筛选语句并逐项审核；图可视化只辅助理解，不代替语句与证据审核。
PR-P0-18 图谱发布。未知类型/关系、非法端点、证据缺失/越界和未解决阻断冲突不能发布；发布、回滚和重同步后核对活动图版本及边数量。
PR-P0-19 GraphRAG 回答。返回图路径、图/文本证据、图版本、检索路由、质量门禁和回退原因；没有正式答案 Provider 时只能返回明确标识的确定性证据摘要。
（五）P0 FMEA 与成果交付
PR-P0-20 模板管理。燃气轮机最小模板 v1.1.0 作为 V1 基线；模板定义字段、关系约束、证据政策、评分政策和导出布局，修改必须创建新版本并重新批准。
PR-P0-21 字段级证据。设备、部件/系统、故障模式、原因、影响、检测方法和建议措施分别保存 evidence_id 和证据明细，不得以整行统一引用替代。
PR-P0-22 人工修订。修改专业字段时必须保留或替换证据；无证据人工补充只能保持待补证/驳回状态，不能直接进入发布。
PR-P0-23 发布与导出。人工批准后方可发布；JSON、CSV、DOCX 的业务字段、证据和版本血缘必须一致，正式 DOCX 使用项目批准模板且不隐藏缺失证据。
（六）P0 身份、审计与闭环
PR-P0-24 统一身份。所有写操作从本地认证或 OIDC/JWT 上下文获取 actor，前端只读展示当前身份，不信任请求体中伪造的 reviewer。
PR-P0-25 职责分离。审核人和发布操作者分别记录；单机模式允许同人兼任，但必须显式写入审计并由项目策略允许。
PR-P0-26 审计记录。记录对象、版本、动作、操作者、时间、原因、修订摘要、correlation_id 和结果；普通日志不得复制完整敏感原文。
PR-P0-27 统一错误。接口错误返回 code、message、stage、retryable、details 和 correlation_id；界面显示用户可执行的下一步。
PR-P0-28 反馈重验证。反馈必须产生根因模块、修复运行和受影响对象清单；修复成功后重新生成或重新验证下游版本，不能只改变反馈状态。
PR-P0-29 验收工作台。显示全部验收门禁、责任角色、所需结构化文件和当前指标；支持证据上传、文件哈希、乐观并发、审计日志和正式验收包生成。
（七）P1 产品化增强
PR-P1-01 支持批量资料审核、批量任务重试、项目模板复制、任务指派和评论；批量操作不得绕过逐项证据和发布门禁。
PR-P1-02 支持电动机等更多设备 Schema、FMEA 模板和报告布局；每个领域必须建立独立金标准和验收阈值，不能继承燃气轮机验收结论。
PR-P1-03 正式控制台按页面模块、API client、状态管理和共享组件组织，保持 Electron 离线运行；模块和样式必须同时在 FastAPI 静态路径下可访问。
六、技术架构与实现要求
（一）部署拓扑与模块边界
V1 由 Electron/浏览器前端、FastAPI 本地服务、后台任务执行器和项目持久化目录组成。默认监听 127.0.0.1；绑定局域网地址时必须启用认证、资源级 project_id 授权、CORS 白名单和传输保护。
data_pipeline 负责接入、解析、OCR 和结构恢复；storage_layer 负责治理事实源、检索投影和图投影；kg_pipeline 负责候选关系抽取；rag_orchestrator 负责检索路由、GraphRAG、FMEA 和修复编排；api_server 负责编排与协议，不复制领域门禁。
（二）核心数据与血缘
TECH-01 Project、SourceAsset、DocumentVersion、EvidenceLocator、IndexSnapshot、GraphVersion、FMEATask 和 DeliveryTask 必须持久化，不以进程内对象或前端状态作为事实源。
TECH-02 所有下游对象携带 project_id、来源版本、created_at、created_by、content hash 和 config hash；FMEA 资料版本必须与图谱来源版本一致。
（三）存储与投影
TECH-03 每项目至少包含 source_assets、governance、retrieval/chroma、graph、exports、logs 和 manifests；项目目录之间物理隔离。
TECH-04 治理数据库是控制面事实源，Chroma 和 GraphStore 是可重建投影。发布资料/图谱触发投影同步；同步失败保留审计并标记 failed，不得把投影标记为 ready。
（四）后台任务与并发
TECH-05 解析、OCR 页重试、索引、图谱抽取、社区摘要、GraphRAG 批量评测、FMEA 和反馈修复必须异步执行，具备租约、心跳、取消、幂等、失败状态、超时和重试分发。
（五）API 合同
TECH-06 /api/delivery 是治理主路径，提供项目、台账、审核队列、资料、图谱、FMEA、任务、审计、健康、血缘、备份恢复和 Provider 接口；列表采用稳定排序与游标分页。
TECH-07 delivery 写接口使用 Idempotency-Key 或显式幂等键和请求指纹；相同请求可重放，不同请求复用键返回 409；更新/发布支持 expected version。
（六）Provider 与数据策略
TECH-08 解析、OCR、翻译、嵌入、图谱抽取和答案生成统一注册为 Provider，暴露 health、capabilities、model/version、timeout、cost class 和 data policy。
TECH-09 外部 Provider 接收原文前执行项目数据策略；涉密项目默认只允许本地 Provider，允许外发时记录提供方、数据范围、模型和调用审计。
（七）安全与权限
TECH-10 单机模式使用本地身份和审计，局域网模式使用 OIDC/JWT；每个 /api/delivery 和验收写接口执行项目/角色授权。
TECH-11 预览、导出、恢复和本地路径只允许访问已登记资产或项目根；拒绝路径穿越、ZIP Slip、任意 file URL 和前端读取系统文件，密钥只从后端安全配置读取。
（八）可观测性
TECH-12 每个请求和任务生成 correlation_id，记录阶段、对象、版本、耗时、Provider、重试和错误；HTTP 返回响应耗时，后台堆栈写入轮转的去敏日志。
TECH-13 项目健康至少覆盖治理库、检索/图投影、Provider、磁盘和最近失败任务，并区分未配置、不可用、退化和健康状态。
（九）备份、恢复与目录安全
TECH-14 项目备份包含项目全目录、治理库、Provider/Schema/模板清单、任务与审计、投影状态和 SHA-256 manifest；恢复前校验路径与哈希，恢复后可重建投影并核对对象数量。
（十）性能与容量
TECH-15 在约定 Windows 参考设备、固定正式资料库和固定嵌入 Provider 上，非 LLM 检索 P95 小于 2 秒、图路径查询 P95 小于 2 秒、页面/证据预览 P95 小于 3 秒；LLM 耗时单独统计。
TECH-16 至少实传 60 MB 资料，接口返回 202 异步任务且不走 Base64，浏览器操作可继续、任务进度可见且无请求超时；OCR 吞吐按具体 Provider 记录。
（十一）不可变目录与验收证据
TECH-17 GraphSchema 和 FMEATemplate 以不可变版本、状态和内容哈希存储；项目复制只复制新项目目录中的独立版本，历史批准版本不可原地覆盖。
TECH-18 验收输入、上传证据、审计和输出必须位于受控证据根目录，阻止路径逃逸；manifest 递归记录文件相对路径、大小和 SHA-256。
七、交互与信息架构要求
（一）正式控制台
控制台至少包含总览、项目/任务、资料台账与审核、检索问答、图谱数据与审核、GraphRAG、FMEA 交付、验收工作台和系统管理。页面围绕业务对象组织，不要求用户手工复制内部 ID 或修改数据库。
（二）证据优先交互
任何答案、图谱语句和 FMEA 字段旁都提供证据入口；证据面板同时显示源文件、版本、页码、块类型、文本/结构、质量问题和审核状态。证据无法打开时必须显示错误，不得用空白面板掩盖。
（三）状态与错误
颜色不是唯一状态表达，所有状态都有文字标签；长时任务持续显示阶段、进度和取消/重试条件；错误信息回答“哪里失败、是否可重试、下一步做什么、关联 ID 是什么”。
（四）审核效率与安全
审核页面支持筛选、原页对照和逐项决定；批量操作明确范围和后果，发布、回滚、恢复等高影响动作显示目标版本并要求原因。不得提供绕过证据门禁的“一键全部通过”。
八、非功能要求
（一）可信性与可复现性
NFR-01 发布内容证据覆盖完整，阻断问题逃逸数为 0，未知内容不推测；相同源资产、版本、Schema、模板和配置可重建同一交付链。
（二）隐私与安全
NFR-02 默认本地存储；密钥不进入前端、导出包和普通日志；文件访问、外部调用和恢复操作受项目策略与明确路径范围控制。
（三）可靠性
NFR-03 写操作幂等，任务可取消/重试，部分失败可恢复，发布和回滚不覆盖历史；进程中断后租约过期任务可被识别并安全接管或标记失败。
（四）性能
NFR-04 常规检索和图路径达到 TECH-15；大文件、OCR、抽取、索引、社区摘要和 FMEA 异步执行，页面主线程不承担计算。
（五）可扩展性
NFR-05 解析器、Provider、向量存储、图存储、领域 Schema 和输出模板通过稳定接口扩展；新增领域不修改核心证据、版本和审核规则。
（六）可观测性与可维护性
NFR-06 阶段耗时、质量问题、失败码、Provider 调用、索引/图版本和审计均可查询；前端模块、API client 和领域服务边界清晰，关键合同有自动化测试。
（七）可访问性与兼容性
NFR-07 关键流程支持键盘操作和文字状态；首要支持 Windows Electron 与本地 Web，依赖缺失时给出安装/配置路径而不是静默降级。
九、成功指标
（一）北极星指标
可信知识交付完成率：进入正式处理的代表性任务中，最终产出经人工批准、版本一致、证据完整且可复现成果的比例。V1 试点目标不低于 80%，但必须以锁定任务清单为分母，不以演示次数替代。
（二）质量指标
1. 证据可解析率：答案引用、已发布图语句和已发布成果字段中的 evidence_id 可解析到有效来源，目标 100%。
2. 阻断问题逃逸数：存在未解决 ERROR 仍进入正式发布的版本数，目标 0。
3. 无证据拒答准确率：应拒答的问题被正确拒答或回退的比例，目标不低于 95%。
4. 导出一致率：同一成果 JSON、CSV、DOCX 经字段与血缘核验一致的比例，目标 100%。
5. 人工复核效率：候选进入审核到正式发布的中位时间，在首批任务建立基线后目标下降不低于 30%。
6. 代表性场景覆盖：原生/扫描 PDF、DOCX、图片、中英文、失败、冲突、回退、回滚和恢复等约定场景覆盖率，目标 100%。
十、V1 验收标准
（一）M2 解析与 OCR
AC-M2-01 试点资料每页必须产生文本/结构结果或经审核的页面级阻断问题，覆盖率 100%；从清晰、低质量、表格、双栏和图片页分层抽样，逐页记录审核人、时间和包内原页证据。
AC-M2-02 对选定金标准页计算字符准确率和关键字段正确率；清晰印刷体字符准确率不低于 95%，未达标页进入人工复核，不使用笼统“准确率 99%”口径。
（二）M3 检索与回答
AC-M3-01 使用至少 10 个经领域专家标注的问题和相关证据块，计算 Recall@5、MRR 和引用可解析率；V1 Recall@5 不低于 80%，展示引用可解析率 100%。
AC-M3-02 题集覆盖无答案、跨型号、冲突来源和版本回滚；无证据问题不得给出确定性答案，同一问题在指定版本和配置下结果可复现。
（三）M4 图谱与 GraphRAG
AC-M4-01 从真实资料建立不少于 100 条人工金标准关系，分别统计实体和关系精确率/召回率；关系精确率不低于 85%、召回率不低于 70%，否则保持人工审核并明确能力边界。
AC-M4-02 已发布图语句证据绑定率 100%，未知类型、非法端点和证据越界逃逸数为 0；普通 RAG 与 GraphRAG 使用同题集并记录路径、回退和专家判断。
（四）M5 FMEA
AC-M5-01 所有非空专业字段证据覆盖率 100%，未知字段保持 null；领域专家逐项标记接受、轻改、重大修改和拒绝，重大修改与拒绝比例不高于 20%。
AC-M5-02 JSON、CSV、DOCX 的字段、证据和任务/资料/图谱/模板血缘一致；未批准评分政策时 S/O/D 和 RPN 必须为空。
（五）端到端产品闭环
AC-E2E-01 一名知识工程师和一名领域审核人仅通过正式界面完成创建项目、接入真实资料、处理问题、发布资料、构建/发布图谱、生成/发布 FMEA、导出成果和处理一次反馈；不得手改 SQLite 或依赖临时脚本。
AC-E2E-02 至少完成一次索引重建、图重同步、资料回滚和项目恢复；自动化验证、人工抽检、专家结论、性能原始记录和已知限制全部进入验收包。
（六）性能与大文件
TECH-15 验收必须在约定 Windows 参考设备、固定正式资料库和固定 Provider 上提交原始耗时及 P95 计算，不以开发机小样本代替。
TECH-16 验收必须提供 60 MB 真实 multipart 上传、202 异步任务、进度界面和观察人签字；只证明接口接受大请求不足以通过界面验收。
（七）验收证据规则
每个通过项必须包含结构化指标、具名审核人、审核时间、包内证据引用和文件 SHA-256。缺少真实金标准或专家决定时状态为 not_evaluated；指标低于门槛时状态为 failed；自动化样例、布尔声明或分类名称不能替代原始证据。
十一、版本范围与发布定义
（一）V1 必须交付
V1 必须交付本地可安装控制台、项目与任务管理、真实资料接入/解析/审核/发布、正式检索与证据问答、受治理图谱与 GraphRAG、带字段证据的 FMEA、反馈重验证、备份恢复、验收工作台、用户说明和可重复验收包。
（二）V1 完成定义
V1 完成必须同时满足：P0 和 TECH 要求连接真实主链；正式界面无需开发者介入；资料、索引、图谱和 FMEA 版本一致；安全和证据门禁有效；第十章全部门禁通过；失败、回滚和恢复可验证；交付文档与安装运行说明完整。代码存在或合成测试通过不能单独构成完成。
（三）V1.5 与 V2
V1.5 扩展更多设备 Schema、模板、批量能力和项目复用；V2 再建设组织级职责分离、可配置审批流、企业系统集成、多团队协作和托管部署。后续能力不得削弱证据、版本和人工发布门禁。
十二、风险、约束与默认决策
（一）数据与领域风险
真实资料缺失、OCR 质量不稳定和专家标注不足是首要风险。默认决策是先锁定燃气轮机试点清单和审核责任人，再调整模型；禁止通过修改演示样例替代金标准。
（二）模型与隐私风险
OCR、嵌入和 LLM Provider 的能力、成本、隐私和输出格式存在差异。默认使用项目批准且可追溯的 Provider；未配置正式 Provider 时明确显示未配置或使用 test-only 能力，不自动外发原文。
（三）投影一致性风险
治理库、向量索引和图存储属于不同运行面，可能出现版本不同步。默认以治理库为事实源，投影记录快照、同步状态和数量；发布、回滚和恢复后必须执行一致性检查。
（四）审核与验收风险
缺少责任人、原始证据或参考设备时，系统能力可以标记“代码已实现”，但产品状态不得标记“验收通过”。默认由验收工作台保留开放项和责任角色，直到真实证据满足门槛。
（五）默认产品决策
1. 产品定位使用“电力装备可信知识交付系统”，V1 业务验收锁定“燃气轮机资料治理 + GraphRAG + FMEA”。
2. 部署默认本地单机；局域网部署必须启用 OIDC/JWT 和项目授权；V1 不做云端多租户。
3. 正式成果默认包含 JSON、CSV 和 DOCX；XLSX 作为后续模板能力，不作为 V1 必过项。
4. 没有批准评分政策时 FMEA S/O/D/RPN 保持空值；证据不足时拒答、留空或回流。
5. 自动化用于生成候选和执行门禁，正式知识与成果由具名人员审核发布。
十三、术语
（一）正式资料
经过源证据检查、质量问题处理和人工批准后发布的不可变 DocumentVersion；默认检索和下游构建只消费正式资料。
（二）证据定位
可稳定解析到项目、资料版本、源资产、页码、块/表/图和可选版面坐标的 EvidenceLocator。
（三）治理图谱
受版本化 Schema、端点、型号、证据、冲突和人工发布门禁约束的 GraphVersion，而不是仅用于展示的关系图片。
（四）可信知识交付
从受控源资料出发，经解析、审核、索引、图谱和专业成果生成，最终形成版本一致、证据完整、可复现和可回滚成果的全过程。
