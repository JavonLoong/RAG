PowerRAG 证据治理与 FMEA 交付工作台
把已存在的 M2–M5 后端能力，变成领域专家可操作、可审核、可发布的产品闭环
文档状态：评审稿

建议产品代号：Governance Workbench / 审核交付台

审计基线：当前工作区；HEAD 6603cf87c5944264907060f4dcec16d3e2445190

产品决策  优先建设“证据治理与 FMEA 交付工作台”，而不是再扩展一个泛化问答页面。当前系统的核心后端闭环已经可执行，最大的产品断层是审核人无法通过主控制台完成治理操作。
0. 执行摘要
PowerRAG 已具备本地文档接入、OCR/解析、正式资料版本、受 Schema 约束的图谱、GraphRAG 问答、FMEA 生成、人工审核、发布、导出和问题回流等后端能力。仓库专项验证在本次审阅中通过 32 项测试，但当前主控制台没有接入 /api/delivery，关键能力主要停留在 API、脚本和测试层。
本 PRD 定义一个面向知识工程师与燃气轮机领域审核专家的本地工作台：用统一任务队列贯穿 M2–M5，在同一界面完成原页与解析结果对照、版本审核与发布、图谱语句证据审计、FMEA 逐字段校核、双格式导出验证以及问题回流。
MVP 的成功标准不是“页面可展示”，而是让一名审核人无需调用 API 或改 JSON，即可从一份待审核资料走到一个带完整证据链、经人工批准且可一致导出的 FMEA 成果。
1. 背景与机会
1.1 当前系统定位
PowerRAG 是一个 local-first 的 RAG / GraphRAG 工作台，当前可运行产品由 FastAPI 后端、单文件前端控制台和 Electron 桌面壳组成。其差异化价值不是单纯聊天，而是把设备资料、图谱关系、检索证据和工程交付成果连接起来。

1.2 核心问题
能力不可操作：后端有完整治理接口，但主控制台未检出 /api/delivery 调用；非开发人员无法完成正式审核。
上下文被割裂：资料、图谱与 FMEA 各自有版本和证据，但缺少一条可视化血缘链来解释“这个字段从哪里来”。
发布风险不可见：阻断级质量问题由后端守门，但用户在点击发布前无法快速理解哪些问题必须先处理。
任务无法管理：现有接口以单个 ID 查询为主，资料与 FMEA 缺少分页列表和跨阶段审核队列。
交付价值未显性化：系统已经能产出可审查 FMEA，但主产品仍被理解为“RAG/GraphRAG 演示工具”。
1.3 产品机会
将已有治理后端包装为真实的人机协作工作流，可以把 PowerRAG 从“技术能力集合”推进为“工程知识交付系统”。这项工作复用现有 M2–M5 能力，新增价值集中在任务组织、审核体验、发布门禁、血缘可视化与必要的列表型 API，投入相对可控，且能形成清晰的演示与验收闭环。
2. 产品定义
2.1 一句话定位
定位  面向电力装备知识工程师与领域专家的本地证据治理工作台，把文档解析、正式资料、受控图谱和 FMEA 成果变成可审核、可追溯、可回滚的交付链。

2.3 产品原则
证据优先：任何衍生事实都能回到稳定的文档版本、文件、页、块或表格定位。
人工决定可追踪：批准、驳回、修改、发布与回滚必须记录操作者、时间和理由。
先门禁，后发布：阻断问题不能靠普通确认绕过；按钮状态必须解释原因。
未知保持未知：缺失字段显示为空与原因，不用模型常识补齐；不自动生成无依据的 S/O/D 或 RPN。
本地优先：MVP 延续 Electron + FastAPI + SQLite/本地存储，不引入云端多租户依赖。
渐进披露：总览显示待办和风险，细节通过证据抽屉、版本差异和审计时间线展开。
3. 目标、非目标与指标
3.1 MVP 目标
打通从待审核资料到已发布 FMEA 的单人完整操作链，不要求用户调用 API。
让审核人对每个资料问题、图谱语句和 FMEA 字段看到对应证据、版本与状态。
把发布门禁和失败原因前置展示，避免“点击后才知道不能发布”。
提供统一任务队列、跨阶段血缘与反馈回流，使问题能回到正确根因模块。
保持现有治理不变量，不因前端便捷性削弱证据、审核或版本约束。
3.2 非目标
不在 MVP 中建设托管式多租户 SaaS、组织级权限和实时多人协作。
不替换现有解析、OCR、向量库、图存储或 GraphRAG 算法内核。
不以本 PRD 承诺提升实体关系抽取精度；模型效果单独走评测体系。
不自动生成无政策依据的严重度、发生度、探测度或 RPN 评分。
不在首版重构整个单文件前端；先以独立路由/模块接入，稳定后再拆分工程。
不把移动端作为首版验收范围。

4.1 关键状态机
资料与图谱状态：candidate → needs_review → published → retired。回滚不会覆盖旧版本，而是生成或恢复可审计版本关系。
FMEA 状态：queued → running → needs_review → approved → published；异常进入 failed。所有迁移保留 from_status、to_status、actor、reason 与 created_at。
门禁规则  资料只在存在证据且最新人工审核为 approve 时发布；图谱只从已发布资料构建且每条语句必须绑定范围内证据；FMEA 只从已发布图谱生成并在人工批准后发布。

5.2 交付总览
顶部指标只显示可行动信息：待审资料、待审图谱、待审 FMEA、ERROR 级阻断、失败任务。
主区域为统一审核队列，默认按“阻断优先、最早进入优先”排序；每行显示阶段、对象、版本、问题数、更新时间和下一动作。
右侧显示运行健康：文档索引版本、当前活动图版本、OCR/翻译/抽取后端连接状态。
空状态提供“载入演示批次”和“上传第一份资料”两个明确入口。
5.3 资料审核页
左栏：原始页图，可翻页、缩放，并显示源文件与页码。
中栏：解析块按阅读顺序排列，显示 block/table/image/caption 类型、坐标和可编辑文本。
右栏：质量问题、OCR 置信度、审核记录与决策面板。点击问题后同时定位原页区域和解析块。
版本模式：支持当前版与上一版差异，明确哪些修订会创建新版本。
发布模式：展示发布门禁清单、即将同步的索引版本和不可逆影响提示。
5.4 图谱审核页
默认表格视图：以语句为最小审核单元，列出主语/类型、关系、宾语/类型、知识类型、型号范围、置信度和证据状态。
问题优先筛选：未知类型、未知关系、端点不合法、证据缺失/越界、来源冲突、低置信度。
证据抽屉：点击语句后显示所有 evidence_id 的原文、文件、页、块以及资料版本。
关系图视图：用于理解局部路径，不作为唯一审核界面；大图自动降级为表格/搜索。
发布前检查：证据审计、阻断问题、来源资料状态与 GraphStore 同步目标必须全部可见。
5.5 FMEA 交付页
任务头：显示所选资料版本、图版本、模板版本、状态、创建人和时间。
交付表：equipment、component、failure_mode、cause、effect、detection_method、recommended_action 七个最小专业字段。
字段证据：每个非空字段显示证据数量徽标；点击打开证据抽屉；无证据字段显式标红。
未知与冲突：空值保持为空并显示原因；冲突信息不可被隐藏，需人工确认或回流。
交付动作：修改、批准、驳回、发布、下载 JSON/CSV、运行一致性验证。

7. 数据与业务规则
7.1 证据显示规则
每条证据最少显示 document_version_id、chunk_id、source_file、text；有值时显示 page、block_id、table_id、image_id。
界面中任何证据徽标都必须可点击并解析到证据详情；无法解析的 evidence_id 视为阻断错误。
图谱证据只能来自该图版本选择的已发布资料版本；越界证据不能通过普通审核绕过。
FMEA 的证据按字段绑定，不只在整行或任务级展示；非空字段无证据时不得发布。
原文、人工修订内容与模型生成内容在视觉上必须区分，避免把候选误认成源证据。

7.3 并发与幂等
MVP 虽为本地单机，也必须避免重复点击产生多次发布或修复运行。所有写操作建议支持 idempotency_key；审核、修订、发布请求携带 expected_version 或 updated_at，服务端发现对象已变化时返回 409，并要求用户刷新后重审。

14. 待产品确认的问题
MVP 的第一试点对象是否固定为燃气轮机/FMEA，还是需要同时覆盖通用企业知识库？建议先固定燃气轮机，以现有 Schema 与模板闭环。
本地单机版的操作者身份如何确定：每次输入 reviewer，还是在设置页固定本机用户？建议设置页固定，可在决策时修改。
资料发布后是否默认自动生成图谱候选？建议默认提示下一步，由用户确认抽取后端与 Schema 后执行。
图谱语句的人工修订是直接保存 corrections，还是创建新的图候选版本？建议任何内容变更都生成新候选版本。
首版是否需要 FMEA 自定义列与企业模板导入？建议 P0 只支持版本化最小模板，P1 再做模板映射。
是否需要在首次试点纳入 S/O/D 与 RPN？建议否，除非提供已批准、证据可绑定的评分政策。
试点成功由谁签字：知识工程师、领域专家还是交付负责人？建议资料/图由领域专家审批，FMEA 由领域专家与交付负责人共同确认。
15. Definition of Done
AC-01 至 AC-12 在代表性原生 PDF、扫描 PDF、DOCX、图片、中英文、OCR 超时/漏页、图冲突和 FMEA 缺证据场景下通过。
用户仅通过 Electron/Web 控制台完成一条 M2–M5 全链，过程中不需要复制对象 ID 或调用 Swagger。
每个发布成果可解析到稳定证据定位；所有人工决定、状态迁移、发布、回滚与回流均可查询。
资料索引、治理图谱、活动 GraphStore 与 FMEA 请求版本一致；不一致时系统明确阻断。
JSON/CSV 导出一致性为 100%；任何无依据的字段保持 null；阻断问题逃逸数为 0。
新增 API 与前端合同有自动化测试；专项 M2–M5 回归继续通过；演示数据和操作手册可重复运行。
试点完成至少 10 个代表性任务，记录审核周期、回流原因和用户反馈，并据此确认 P1。
