一句话定位

先把项目说清楚，再展开技术细节。

最稳的答辩开场

PowerRAG 是一个面向动力装备资料的可信问答系统。它不是把问题直接丢给大模型，而是先把 PDF、扫描件、JSON 标注、OCR 文本和维修资料处理成带来源、页码、章节、metadata 的证据块，再用关键词、向量、混合检索和 GraphRAG 找证据，最后让回答能够回到原文依据，并通过评测持续改进。

资料接入 证据构建 混合检索 GraphRAG 评测闭环

技术路线图

这是主讲结构：从资料到答案，不从页面开始讲。

Step 1 资料入口 PDF、扫描件、JSON、TXT、DOCX、CSV 进入上传区或批量目录。
Step 2 文档解析 按 source kind 选择 native、DeepDoc、MinerU、Docling、Unstructured 或 OCR 路线。
Step 3 分块与 metadata 保留 source_file、页码、章节、chunk id、block 类型、解析诊断和 preview。
Step 4 Chroma 入库 按批次 upsert 到集合，默认追加或覆盖同 ID，不是上传瞬间自动入库。
Step 5 Hybrid 检索 Chroma vector、keyword、metadata filter、RRF 融合，可选 query rewrite 和 reranker。
Step 6 GraphRAG 实体、关系、evidence、community summary 支撑 local / global 问题。
Step 7 回答与评测 答案绑定证据，评测召回、覆盖、引用、失败归因和下一轮优化。

对标与借鉴

用“借鉴”和“对标”表达，不要在正式材料里说抄袭。

RAGFlow

重点借鉴文档解析、chunk preview、metadata、解析诊断和知识库产品化思路。我们已搬入入口和流程思想，但没有完整复刻它的深度版面解析底座。

重点借鉴 pipeline 化、hybrid retrieval、metadata filter、query rewrite、property graph 和可组合检索器的工程边界。

重点借鉴 local / global 分工、community summary、轻量图检索和“图谱增强而不是替代”的定位。

行业头部的说法要谨慎

RAGFlow、Haystack、LlamaIndex、Microsoft GraphRAG、LightRAG 可以算开源头部或重要开源参考，但开源头部不等于整个行业绝对顶尖。真正生产级还要对标云厂商托管 RAG、企业搜索、权限审计、任务队列、可观测性和专家评测。面向清华燃气轮机所时，正确说法是：我们正在按开源头部和企业级系统的共同标准补齐能力，而不是宣称已经达到闭源工业系统的最终水平。

当前本地评测不是按单一设备类型划分，而是按问题任务和资料来源划分。字段上有 task_type、source_scope 和 expected_modes，覆盖事实问答、流程问答、结构化数据、对比问题、OCR 风险、GraphRAG、回答质量和评测方法。后续更专业的版本应该再补 equipment_type、fault_type、complexity 和专家标准答案。

答辩问答库

这里放刚才连续追问的可直接回答版本。

Q1：系统现在的向量库更新机制是怎样的？新资料入库是实时更新还是批量处理？会不会影响正在问答？
可直接回答： 目前系统的向量库更新机制更准确地说是批量触发式更新，不是严格意义上的实时流式更新。

新资料进入系统后，不是上传完立刻就能被问答检索到，而是要经过一套入库流程：先保存上传文件，再解析文本、清洗、分块、生成 metadata，然后对每个 chunk 做向量化，最后写入 ChromaDB 向量库。这个过程完成以后，新资料才会进入检索范围。

对于普通新增资料，系统主要是用 upsert 的方式把新的 chunk 写入已有集合，所以不会把整个服务停掉。正在进行的问答一般还能继续查旧数据，只是如果同时在跑大批量入库，可能会占用 CPU、磁盘 I/O 或 embedding 模型资源，导致问答响应变慢。

边界说明： 如果是整批资料重建，或者某些数据集采用“删除旧集合再重建”的方式，那在重建期间就可能出现短时间检索不完整的问题。所以目前系统还不是企业级的“无感热更新”。更稳妥的答辩说法是：当前系统采用批量入库、增量 upsert 为主的向量库更新机制。新增资料需要经过解析、分块、向量化和写库后才会被检索到。一般新增不会中断正在进行的问答服务，但大批量入库会带来资源竞争，可能影响响应速度。后续如果要支撑正式在线服务，需要引入后台任务队列、索引版本管理和蓝绿切换机制，保证新索引构建完成后再原子切换，避免检索结果在更新过程中不稳定。
Q2：60 道评测题是按什么维度覆盖动力装备核心场景的？

这里要先纠正口径：当前仓库里实际可见的 evaluation/system_eval_questions.jsonl 是 47 题，不是完整 60 题；Day3 baseline 报告里跑的是 30 题检索子集。旧 HTML 或早期材料里出现过 60 题口径，答辩时不要把两个版本混在一起。

可直接回答： 评测题不是简单按设备类型划分，而是按问题能力来覆盖：事实参数查询、流程机制解释、结构化数据查询、跨文档对比、OCR 风险、GraphRAG 关系型问题、回答质量和评测方法。资料来源上再通过 source_scope 区分燃气轮机原理、联合循环、维护可靠性、课程资料和 GraphRAG 子集。

如果要做到清华燃气轮机所级别，下一版应该补设备维度，比如压气机、燃烧室、涡轮、余热锅炉、控制系统；再补复杂度维度，比如单段事实、多段综合、跨设备对比、故障归因和 no-answer。

Q3：失败归因后，针对片段不精准，除了引入 reranker，还做过什么优化？
可直接回答： 做过一些针对性优化，但还没有完成严格的 chunk-size 消融实验。已经做的包括：用标题和段落断点触发 chunk 边界，保留页码、来源、章节、block 类型等 metadata；给 chunk 加 overlap，避免关键句被切断；在文档解析结果里提供 chunk preview，方便人工检查切分是否合理；搜索时也加入 source file、年份、作者等 metadata filter，减少召回范围过宽。

还需要继续补的是系统化实验：对不同资料类型分别测试 500/50、900/120、1200/150 等 chunk_size 和 overlap，比较 recall、coverage、citation 命中和人工可读性。也就是说，当前有工程优化，但还不能说已经完成最优分块参数搜索。

Q4：系统落地后，用户问得最多的是哪类问题？参数查询、故障分析还是跨文档对比？

这里不能假装已经有大量真实用户日志。更稳妥的说法是：目前主要依据评测题和动力装备资料使用场景来判断，而不是依据大规模线上用户统计。

可直接回答： 从目前测试和场景推断，最常见的是三类：第一类是参数和定义查询，比如某个部件的作用、某个循环为什么效率高；第二类是机制和流程解释，比如压气机、燃烧室、涡轮之间的能量转换关系；第三类是故障、维护和跨文档对比，比如某个故障可能关联哪些部件，或者不同资料对同一设备边界条件的说法是否一致。

其中普通 RAG 更适合前两类直接证据问题，GraphRAG 更适合第三类关系追踪和跨文档综合问题。

Q5：为什么把 GraphRAG 定位成增强路线，而不是替代传统 RAG？依据是什么？
可直接回答： 这个判断来自前期 baseline 和失败归因。Day3 检索结果里，keyword 的 question recall@K 是 0.833333，hybrid_rrf 是 0.8，dense_hashing 是 0.6。这说明在动力装备资料里，强术语和明确部件名非常重要，简单事实题不一定需要走复杂图谱，直接关键词或混合检索反而更稳。

GraphRAG 的价值不在于替代所有检索，而在于处理普通 top-k chunk 不擅长的问题：实体关系、多跳因果、跨文档综合和全局社区摘要。所以技术路线是先判断问题类型，事实类走标准 RAG，关系类和全局综合类再走 GraphRAG。

Q6：动力装备领域有行业黑话和缩写，问题预处理怎么解决术语理解？
可直接回答： 当前主要靠四层机制：第一是关键词检索保底，保证 M701F、HRSG、压气机、燃烧室这类强术语不会被语义模型稀释；第二是可选 query rewrite，把用户口语问题改写成更完整的检索表达；第三是 metadata filter，按文件、来源、年份、作者、设备对象缩小范围；第四是 GraphRAG 实体层，把同义实体、部件关系和 evidence 绑定起来。

但要诚实说，现在还没有完整的专家术语词典和缩写表。下一步应该建设燃气轮机领域 glossary，包括中英文缩写、设备别名、型号别名、故障别名和单位表达，再接入 query rewrite 与实体归一化。

Q7：系统现在支持多轮对话吗？追问“这个参数在另一台设备是否适用”能不能关联上下文？
可直接回答： 系统支持基础的多轮会话记忆，但复杂追问还不能说完全成熟。现在后端有 session、message、summary 和 memory vector store，可以按会话保存历史问答、读取最近几轮上下文、把长历史压缩成摘要，也可以对摘要做记忆检索。

限制在于核心 RAG 查询链路还没有完全自动把 memory context 接入 query rewriting。比如上一轮问“M701F 排气温度上限是多少”，下一轮问“这个参数在另一台同类型设备上是否适用”，系统必须先把“这个参数”改写成“M701F 排气温度上限”，再把“另一台设备”解析成具体设备型号，然后再检索。这个上下文改写链路还需要继续补齐。

Q8：RAGFlow 的文档解析底座搬过来了吗？复刻程度大概多少？

不能说完全搬过来了。更准确的说法是：我们把 RAGFlow 的产品思路和关键工程接口搬进来了，但没有完全复刻它的全套底座。

可直接回答： 目前复刻的是 60% 到 70% 的思路层和工程接口：多格式资料入口、解析路线记录、chunk preview、metadata、入库摘要、解析失败诊断、知识库统计。这些已经能支撑课程项目和初步演示。但 RAGFlow 更强的地方在复杂版面解析、表格图片理解、多模型解析编排、任务队列和知识库产品化管理，这些还没有完全搬完。
Q9：如果现在只有 40 分，常见 RAG 系统一般能跑多少？我们该怎么系统优化？

40 分不能简单理解成系统彻底不行，它通常说明评测链路里有多个短板叠加：解析质量、chunk、embedding、召回、排序、引用和 GraphRAG 都会影响总分。

可直接回答： 常见开源 demo 在自己熟悉的小数据上可以看起来很高，但一到真实扫描件、中文教材、专业术语和跨文档问题，分数会明显下降。我们的优化顺序应该是：先稳文档解析和 metadata，再换轻量但正式的 embedding，再调 hybrid 权重和 reranker，再补 GraphRAG local/global 同题评测，最后把 no-answer、citation 和专家题库做起来。

不要一上来大换血。先在本地框架里把 embedding、chunk、hybrid、reranker 和评测闭环调稳，确认收益后再考虑更大的架构调整。

Q10：资料解析入库时，面对动力装备里的大量图表和公式，系统怎么让后续检索也能关联到这些非文本内容？
可直接回答： 我们处理图表和公式的思路，不是把它们当成普通图片丢掉，而是尽量把它们转成可检索的文本证据，加上可回溯的位置 metadata。

动力装备资料里很多内容不是纯文字，比如结构图、性能曲线、参数表、公式推导。系统入库时会先做版面解析，把页面里的正文、标题、表格、公式、页码等内容拆出来，并给每个内容块打上类型标记。比如一个 chunk 里面会记录它来自哪本资料、哪一页、哪个章节，以及它包含的是 text、table、equation 还是混合内容。

对于表格，我们尽量保留表头、单位、行列关系，把它转成 HTML 或类 Markdown 文本。这样用户问“某型号压气机参数是多少”“某个温度范围是多少”时，检索系统不是只搜正文，也能搜到表格里的字段、单位和数值。

对于公式，我们会把公式转成 LaTeX 或文本形式，并且尽量和公式前后的解释放在同一个上下文块里。因为单独一个公式往往不好检索，真正有价值的是“这个公式描述什么、变量代表什么、适用条件是什么”。所以我们在分块时会尽量保留公式编号、变量说明和上下文解释。

对于图片和结构图，目前更准确地说，我们主要依赖图题、图注、OCR/VLM 提取出来的文字，以及图前图后的说明文字来建立检索关联。也就是说，系统现在不是直接对图片本身做强多模态理解，而是先把图片周围的语义信息转成可检索文本，再通过页码和来源 metadata 回到原始资料。

边界说明： 当前系统对图表公式采用的是“版面解析 + 文本化表达 + 来源绑定”的方式。表格会保留表头、单位和数值，公式会保留 LaTeX 表达和变量说明，图片主要通过图题、图注和相邻段落建立语义索引。但目前还没有完全做到对所有图片内容进行端到端多模态检索。如果图里没有图注、没有可 OCR 的文字，系统理解能力仍然有限。下一步可以加入图像区域裁剪、图表 caption 生成、表格结构化抽取和多模态 embedding，让图表公式的检索能力更完整。
Q11：最终生成答案时，怎么平衡检索资料准确性和大模型语言流畅度？会不会出现模型为了通顺修改专业数据？
可直接回答： 这是我们特别需要控制的点。我们的原则是：专业事实和参数必须服从检索证据，大模型只负责组织表达，不能自由改写数据。

在最终生成答案时，系统会先检索出相关 chunk，把原文证据、来源文件、页码、章节和相似度一起传给生成模块。大模型回答时不是凭自己的知识直接发挥，而是要围绕这些证据生成答案。对于参数、公式、设备型号、故障原因、操作条件这类专业信息，优先使用原文里的表达和数值。

比如资料里写的是某个温度范围、压力范围、间隙值或者公式变量定义，模型不能为了句子更顺把数值四舍五入、换单位或者扩大适用范围。它最多能做的是把原文解释得更清楚，比如把长句拆开、把结论放前面、把依据列出来。

答案要求可以概括成三层：第一，结论要有证据，没有检索到依据就不能硬答；第二，参数要忠实原文，型号、数值、单位、公式、适用条件不能被模型润色变形；第三，语言可以整理，大模型可以把多个证据组织成更容易读的回答，但不能牺牲专业准确性。

边界说明： 当前系统还不能百分百保证模型永远不改动专业数据，所以工程上还需要继续加强约束，比如答案里强制引用来源、对数值和单位做后处理校验、对无证据问题返回“不足以判断”，以及把生成结果和检索证据做一致性检查。答辩时可以说：我们把大模型定位为“证据组织器”，不是“知识来源”。检索结果决定事实边界，大模型负责把证据组织成自然语言。
Q12：实际操作中，系统怎么自动把答案证据和来源页码精准绑定？扫描版 PDF 怎么定位到具体段落位置？
可直接回答： 我们做证据绑定的核心思路是：不是等答案生成完再去找来源，而是在资料入库时就把来源信息绑定到每个 chunk 上。

资料解析入库时，每个文本块都会带 metadata，比如来源文件名、页码、chunk 编号、章节标题、内容类型、OCR 来源和处理版本。如果有版面解析结果，还会保留页面块的位置关系。后续检索时，系统返回的不是一段裸文本，而是文本内容、来源文件、页码、chunk_id 和 metadata 一起返回。

所以最终生成答案时，引用不是模型自己编的，而是从检索结果里带出来的。模型负责组织语言，证据来源由系统结构化 metadata 提供。

对于扫描版 PDF，难点是它本身没有可复制文本，也没有天然段落结构。我们的做法是先经过 OCR 和版面解析，把每一页拆成多个文本块，并尽量保留标题、段落、表格、公式和页码信息。这样系统至少可以把答案定位到“哪本资料、哪一页、哪个 chunk”。如果 OCR 结果里有坐标信息，还可以进一步定位到页面上的具体区域，比如某个段落块或表格块。

边界说明： 目前系统最稳定的是页码级 + chunk 级定位，还不能保证所有扫描 PDF 都做到像网页锚点一样精准定位到每一个自然段。扫描件质量、版面复杂度、两栏排版、表格跨页都会影响段落定位精度。复杂扫描件下，段落级精准定位仍然是后续需要继续优化的部分。
Q13：OCR 识别会不会出现文字错乱或段落拆分错误？有没有校验或修正机制，避免错误 metadata 影响检索和溯源？
可直接回答： 会有，而且这个问题必须正面承认。扫描版 PDF 的 OCR 不可能完全干净，常见问题包括文字识别错、两栏顺序错乱、表格被拆碎、公式和正文混在一起、页眉页脚被当正文、段落被错误切开。这些都会影响后续检索，尤其会影响 metadata 和页码溯源的可信度。

我们现在的处理思路分几层。第一层是版面感知解析，不是简单按整页文字从上到下拼接，而是尽量识别标题、正文、表格、公式、页码、图题这些块类型，减少两栏排版和表格造成的顺序混乱。

第二层是清洗和过滤。系统会处理明显的噪声，比如页眉页脚、孤立页码、过短碎片、重复文本、乱码比例高的片段，避免很多低质量 OCR 文本直接进入向量库。

第三层是保留 OCR 质量信息和来源版本。chunk 的 metadata 里会保留来源文件、页码、解析方式、OCR 版本、内容类型等信息。这样后面如果某条证据明显有问题，可以追溯到是哪本书、哪一页、哪个 OCR 版本产生的，而不是只看到一段孤立文本。

第四层是人工抽检和质量审计。之前我们对 OCR 结果做过质量审计、低置信度页重识别、夜间总检矫正这类流程。它的作用就是把明显不可靠的页找出来，重新识别或标记风险。

边界说明： 目前还没有完全做到所有 OCR 错误自动修正。更准确地说，系统现在能做的是：减少明显噪声、保留溯源、发现低质量页、支持重新处理；不是保证每一页 OCR 都绝对正确。后续会继续加强 OCR 置信度评分、版面坐标校验和人工复核闭环。

后续路线

按最能涨质量的顺序排，不按炫技程度排。

1. 文档解析继续补强

把表格、图注、标题层级、页眉页脚、跨页段落和 OCR 低置信度诊断做成可检查报告。目标是降低垃圾 chunk 和错页引用。

2. 轻量正式 embedding + reranker

优先使用小巧中文/多语种 embedding 和本地 reranker，不下载超大模型。用同一评测集比较 keyword、vector、hybrid、rerank 的收益。

3. GraphRAG 同题实测

把关系型、跨设备、跨文档、全局总结问题单独成组，对比 standard RAG、local GraphRAG、global GraphRAG 和 hybrid graph。

4. 生产级更新机制

把当前同步批处理升级为后台任务队列、staging collection、索引版本、评测通过后切换和失败回滚，避免大批量入库影响在线问答。
